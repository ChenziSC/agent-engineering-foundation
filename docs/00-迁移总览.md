# 迁移总览

## 目标

将已有实践中真正通用的 Agent 工程能力重新整理为一个独立、可扩展的公开技术底座。

这里的“迁移”不是复制文件，而是完成三件事：

1. 找出原能力中可跨项目复用的设计；
2. 把这些设计重新组织成清晰的通用模块；
3. 用独立表达和合成案例说明它仍然成立；只有可运行产物才要求行为评估或程序测试。

## 两套产物

迁移过程同时维护两套产物。

### 公开仓库

公开仓库只包含：

- 通用问题定义；
- 独立设计的接口和 Schema；
- 独立编写的框架、Skill、模板和 Blueprint；
- 合成示例；
- 可运行产物所需的测试与 Eval；
- 按需提供的参考实现；
- 公开来源说明。

### 本地私有台账

本地私有台账用于：

- 记录看过哪些来源区域；
- 标记每个关键设计被沉淀到哪里；
- 记录哪些内容被排除；
- 记录公开版本用什么方式替代；
- 防止一对多拆分后遗漏关键信息。

私有台账不进入 Git，也不作为公开仓库的一部分。

## 映射方式

允许使用四种映射：

| 映射方式 | 说明 |
| --- | --- |
| 一对一泛化 | 一个原始能力重写成一个通用能力 |
| 一对多拆分 | 一个成熟能力拆成框架、Skill、模板、Adapter 草案或 Eval 方法 |
| 多对一合并 | 多个相似能力合并成一个通用模式 |
| 横向抽取 | 从多个能力中提取共同协议或基础设施 |

因此，公开仓库不需要和任何原始仓库保持目录对应。

## 判断迁移是否完整

不按文件数量验收，而按能力信息验收。每项能力至少要回答：

1. 解决什么问题；
2. 什么时候触发；
3. 必需输入和可选输入是什么；
4. 产出什么；
5. 核心流程和状态如何变化；
6. 哪些步骤由 Agent 判断；
7. 哪些步骤必须由程序确定性执行；
8. 有哪些人工确认点；
9. 常见失败模式是什么；
10. 如何验证结果；
11. 外部系统如何替换；
12. 距离生产可用还缺什么。

## 第一阶段范围

第一阶段的能力范围包含八个 P0 能力：

1. Web 首屏预请求；
2. 长任务 Checkpoint；
3. Spec 驱动研发流程；
4. Skill 运行时与分发；
5. 证据与推断模型；
6. Skill 行为评估；
7. AI 友好仓库；
8. Web 性能评审。

“进入第一阶段范围”只代表需要完成边界设计，不代表八项能力同时开始编码，也不代表价值排序就是实施顺序。实施顺序以依赖关系和纵向可验证性为准，详见[能力地图](01-能力地图.md)。

每项能力先选择[交付形态与成熟度](05-交付形态与成熟度.md)，再决定是否需要代码。

## 方案阶段完成条件

一项能力只有同时满足以下条件，才算完成方案定义：

1. 使用统一的[能力说明模板](04-能力说明模板.md)；
2. 标明首期交付形态以及未来可选工程化形态；
3. 明确调用或触发条件，以及不适用场景；
4. 定义必需输入、可选输入和输出；
5. 明确 Agent、确定性程序和人工确认的职责；
6. 明确依赖方向和唯一事实来源；
7. 明确非目标、安全边界和外部系统替换方式；
8. 至少设计三个完全合成的应用案例；
9. 给出与交付形态相匹配的首版验收条件。

第一阶段不以“创建了多少目录”作为完成标准。

纯设计框架可以通过文档评审和案例走查验收；可使用 Skill 必须补行为 Eval；只有实际存在确定性脚本或 Package 时才要求程序测试。
