# 交付形态与成熟度

本仓库以 Markdown 为主要载体，不把所有通用能力都强制实现为代码。

## 首期交付形态

| 形态 | 主要内容 | 首期是否必须可运行 |
| --- | --- | --- |
| 设计框架 | 问题模型、对象、边界、状态、决策规则和失败模式 | 否 |
| Blueprint | 数据流、契约草案、扩展点、安全边界和生产化缺口 | 否 |
| 模板 | 可复制修改的 Markdown、YAML 或 JSON 骨架 | 否 |
| 可使用 Skill | `SKILL.md`、references、assets 和行为案例 | 是，指 Agent 可按说明执行 |
| 参考实现 | Package、CLI、Adapter、脚本、测试和自动化 Eval | 是，但首期默认不要求 |

“可使用 Skill”不等于必须包含代码。没有确定性脚本时，可以只有 Skill 指令、参考资料、模板和行为 Eval。

## 成熟度标记

每项能力使用以下标记之一：

| 标记 | 含义 |
| --- | --- |
| `idea` | 只有候选方向，尚未完成边界设计 |
| `designed` | 问题、输入输出、职责、边界和案例已经明确 |
| `usable` | Skill 或模板可以被个人项目直接采用 |
| `reference-implemented` | 已提供可运行的参考实现 |
| `validated` | 已通过对应的行为 Eval 或程序测试 |

设计框架达到 `designed` 就可以作为有效沉淀，不要求继续升级。

## 升级原则

只有满足以下任一条件，才把设计框架升级为参考实现：

- 已经有两个以上真实使用方需要相同的确定性能力；
- 人工执行频繁出错，代码可以显著降低错误；
- 需要机器校验稳定的 Schema、状态机或安全门禁；
- 可运行实现本身具有独立复用价值。

不要为了让仓库“看起来完整”而创建空 Package、空脚本或空测试目录。
