# 目标仓库设计

## 设计原则

仓库按“设计原因—项目采用—确定性执行”分层，而不是按来源仓库、公司平台或编程语言组织。目录只有在存在真实产物时创建，不保留空目录。

```text
agent-engineering-foundation/
├── AGENTS.md               # Agent 工作入口与全仓不变量
├── README.md               # 面向使用方的定位和入口
├── docs/                   # 能力地图、成熟度和发布规则
├── knowledge/              # 长期稳定事实、契约和范围路由
├── specs/                  # 仓库自身的当前研发事项与验证证据
├── frameworks/             # 通用问题模型和设计不变量
├── skills/                 # Agent 可直接执行的能力
├── templates/              # 不属于单一 Skill 的可复制资产
├── blueprints/             # 接入设计、扩展点和生产化缺口
├── starter/                # 项目快速接入骨架
├── packages/               # Harness 和未来确定性内核
├── adapters/               # 当前 Host 与未来 Provider 适配
├── distribution/           # 可分发 Skill 白名单与内容摘要版本
├── .github/workflows/      # 当前仓库的最小 CI 门禁
├── examples/               # 未来按需：完全合成的组合示例
├── scripts/                # 未来按需：仓库级确定性检查入口
└── pets/                   # 与主体依赖隔离的可选附加资源
```

`starter/`、`packages/harness/` 和 `adapters/open-agent/` 已有实际产物；`examples/` 和 `scripts/` 尚无独立产物，因此不创建空目录。

## 设计原因与长期知识

### `frameworks/`

定义跨项目问题模型、对象所有权、状态、决策规则、失败模式和未来接口。框架达到 `designed` 即可成为有效资产，不要求附带程序代码。

当前包括 Evidence、Checkpoint、Skill Eval、Web Prefetch 和项目组件治理。

### `knowledge/`

保存跨任务稳定的仓库定位、设计原因、契约、代码入口和刷新条件。Registry 负责发现，Code Entry Map 负责按任务范围路由。Knowledge 不保存当前任务进度，也不复制 Specflow 状态。

### `docs/`

保存面向维护者和采用方的能力地图、目标结构、成熟度、公开边界和发布规则。README 只提供入口，稳定规则放 Knowledge，当前工作状态放 Spec。

## 项目采用与 Agent 执行

### `skills/`

每个 Skill 使用独立目录，并按需包含：

```text
skill-name/
├── SKILL.md
├── agents/
├── references/
├── assets/
├── evals/
├── scripts/      # 只有确实需要确定性动作时
└── tests/        # 只有存在脚本或 Package 时
```

当前可分发 Skill 以 `distribution/manifest.yaml` 和 `skills/` 真实目录为准，不在设计文档中维护固定数量或正式回放名称清单。各资产成熟度及证据入口统一见[交付形态与成熟度](05-交付形态与成熟度.md)；Runner 不锁定模型或推理强度。

### `templates/`

保存不属于单一 Skill、可以被项目复制修改的仓库规则、Knowledge、Skill Eval、Skill Runtime 和组件治理模板。Skill 直接使用的输出模板放在对应 `assets/`，避免双写。

### `blueprints/`

保存已经完成边界设计、但尚无完整通用实现的能力。Blueprint 必须包含问题、数据流、契约、职责、安全边界、失败模式和生产化缺口，不接受只有目录名的占位设计。

### `starter/`

Starter 是采用入口，不是另一套框架正文。首版只包含一个最小 Preset：

```text
starter/
└── minimal/
    ├── AGENTS.md
    ├── specs/
    ├── knowledge/
    └── agent-foundation.json
```

该 Starter 已由 T-06 实现和验证。JSON Manifest 不替代项目自己的业务配置，其字段分为三类：

- 执行契约：`directories`、`context`、`integrations` 和 `safety`，必须被 Harness 消费或校验；
- 已校验声明：`schemaVersion` 和 `preset`，用于选择受支持的契约；
- 描述性元数据：`metadata.description`、`metadata.documentationRef` 和 `metadata.labels`，可以辅助人和 Agent 理解，但不产生执行或安全效果。

辅助理解字段可以保留，但必须放在明确的描述区域、限制类型和体量，不能使用看似安全策略却未被执行的“死字段”。

### 已有项目接入

已有项目不应直接假设 Starter 可以覆盖写入。先执行只读计划：

```bash
node packages/harness/bin/agent-foundation.mjs init plan --target /path/to/existing-project
```

计划将每个 Starter 文件标记为新增、已存在且相同，或同路径冲突。只有无冲突时才执行 `init`；冲突内容由采用方人工合并，Harness 不猜测业务规则。计划和写入都会拒绝目标路径任一已存在父级或自身为 Symlink，防止从表面项目路径写入其他位置。

### 项目 Harness 化接入路径

本仓提供的是通用项目级 Harness 化脚手架与参考底座。采用方应把接入理解为分阶段建立工程环境，而不是把 Starter 文件复制成功当作完成：

1. **建立项目上下文**：初始化规则、Knowledge、Specflow 和 Integration Manifest，并由项目维护者补充真实入口、不变量和未确认项；
2. **接入 Agent 能力**：按需安装通用 Skill，增加项目专属 Knowledge 与领域 Skill，不把所有能力默认打包；
3. **启用确定性门禁**：在本地或 CI 运行 Doctor、Specflow、Knowledge、Distribution 和适用的 Validator；
4. **连接真实基础设施**：通过显式 Adapter 接入项目已有的版本控制、浏览器、设计、工作项、发布和遥测系统；
5. **形成项目级验证闭环**：由采用方补齐语言级构建、测试、Lint、运行沙箱、审批策略、观测和业务验收。

| 边界 | 本仓职责 | 采用方职责 |
| --- | --- | --- |
| 通用治理 | 提供规则骨架、上下文契约、Specflow、Evidence、Checkpoint 和通用 Skill | 写入项目事实、业务约束、责任人和领域验收条件 |
| 确定性执行 | 提供 Starter、Harness、Doctor、Validator、开放 Host 和 Adapter 契约 | 选择门禁、接入项目工具链，并维护公司或项目专有 Adapter |
| Agent 运行时 | 提供可被运行时消费的项目资产和扩展边界 | 提供真实模型调用、工具权限、沙箱、状态存储、观测和发布运行环境 |

因此，当前仓库可作为 Harness 化接入起点和通用内核，但不单独构成完整 Agent Runtime 或开箱即用的企业研发平台。

## 确定性执行

### `packages/`

当前 `packages/harness/` 已实现以下最小职责：

- 项目初始化与幂等更新；
- Skill 发现、检查、安装计划和安全写入；
- Distribution Manifest 的项目级 Plan/Apply/Verify；
- Repository Doctor；
- Specflow 完整 Meta、产物、本地关系与终态链检查；
- Active Spec 与 Knowledge 最小上下文解析；
- 可配置的单事项/总全文预算，以及超限时的 Markdown Section Index；
- 按请求路径发现根级与祖先规则，并检查规则文件预算、精确继承重复、失效入口和结构性路由矛盾；
- Knowledge Registry 引用、路径和权威来源摘要检查；
- Knowledge Projection 的 Plan/Apply/Verify、路径反向覆盖、状态/取代关系和来源摘要更新；
- 本地 Git Merge Candidate 的范围化变更摘要与脏工作区/冲突阻断；
- 完整候选上的一个或多个 Spec 显式关联、Scope 并集覆盖或受控路径型豁免，以及交付阶段逐项 Receipt/Lifecycle 摘要复核；
- 仓库目录、JSON/JSON Schema、YAML 子集、Markdown 链接、Skill/Eval、高置信秘密格式、无扩展名文本和敏感路径检查；
- 可选的暂存区、Git 历史、Reflog 和不可达对象扫描；
- Evidence Bundle、Skill Eval Replay/Scorer 与项目组件 Registry 的确定性检查；
- 结构化、稳定且可操作的错误输出。

Specflow 已提供完整 Meta Schema 与仓库级检查、单事项目录内 Receipt、Lifecycle Event、Meta 状态最后写，以及同一 Specs Root 下双终态事项关系事务脚本；Harness 另提供 Active Context 解析、确定性全文预算、Section Index、祖先规则导航、Knowledge 来源摘要检查、Projection Registry 更新、本地 Git Merge Candidate 摘要和两阶段 Change Gate。Active 事项关系事务、三个及以上事项关系事务、跨仓库关系事务、其他版本控制 Provider、受保护历史、自然语言规则冲突判断、Knowledge 正文生成和刷新触发的语义判断仍是后续能力。

Package 不负责理解业务意图，也不自动调用外部系统。只有稳定、机械、反复执行且需要测试的步骤才进入代码。

Checkpoint、Evidence 和 Specflow 的状态所有权保持分离：

| 对象 | 唯一所有者 |
| --- | --- |
| Evidence、Claim、Blocker、Verification | Evidence Bundle v1 与语义评审者 |
| Run、Stage、Event、Decision、ExternalRef | Checkpoint 模型或未来 `checkpoint-core` |
| Draft、Planned、In Progress 和终态 | Specflow Meta |
| Receipt、归档后 Lifecycle Event | Specflow Archive 契约 |
| 长期事实和刷新状态 | Knowledge 与 Registry |

### `adapters/`

Adapter 只处理宿主和 Provider 差异：

```text
adapters/
├── registry.mjs       # 显式注册和注入，不动态扫描代码
├── open-agent/        # 当前项目级 .agents/skills Host
├── host/              # 采用方可在自己的仓库实现其他宿主
├── source-control/    # 版本与 Merge Candidate 证据
├── browser/           # DOM、Network、Console 和截图证据
├── work-item/         # 外部工作项，可选
└── mock/              # 合成端到端测试
```

默认仓已实现一个开放 Host、本地文件系统和本地 Git Source Control Adapter；T-08 增加显式 Adapter Registry 与 Integration Manifest。采用方可以在自己的仓库注册其他 Host 或基建 Adapter，不需要把私有实现复制到本仓；动态插件加载、真实平台 SDK 和凭证解析不属于公共核心。

跨能力的注册、状态和凭证引用边界见[项目基建 Adapter Blueprint](../blueprints/infrastructure-adapters/README.md)。能力级输入输出仍由 Host、Source Control、Work Item、Design Input、Browser Evidence、Release 和 Telemetry 分别定义。

## 自举治理

仓库自身使用 `specs/`、`knowledge/` 和根 `AGENTS.md`：

1. Meta 选择相关 Active 事项；
2. Code Entry Map 加载相关 Knowledge；
3. Spec、Plan 和 Tasks 管理范围、方案和执行；
4. Validation Report 保存真实验证；
5. 明确终态授权后，Receipt 和 Event 冻结收口证据；
6. 稳定结论投影到 Knowledge。

步骤 1～4，以及步骤 5 的本地 Git 摘要、单事项目录 Receipt/Event/Meta 和双终态事项 Relation Transaction 已有参考实现。具体事项是否具备终态授权和可归档的不可变 Source，只能从该事项的 Meta、Git 候选与 Receipt Evidence 判断，本设计文档不复制当前工作区状态。Active 事项关系事务、三个及以上事项关系事务、跨仓库关系事务与 Knowledge 正文更新仍未自动化，因此不能把实现存在等同于事项已经归档。

## 示例、评估与测试

- Skill 行为案例优先放在该 Skill 的 `evals/`；
- 跨 Skill 案例只有真实需要时才建立顶层 `evals/`；
- 纯框架和 Blueprint 使用合成案例走查；
- 确定性 Package、Script 和 Adapter 必须有自动化测试；
- 所有公开 Fixture、URL、版本和数据必须自行构造。

## 附加资源

`pets/` 可以保留在同一仓库，但不参与 Agent 工程能力的依赖关系、成熟度或 Harness 安装 Preset。
