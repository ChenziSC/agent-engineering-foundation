# 目标仓库设计

## 设计思路

目标仓库按“通用框架—Agent Skill—复用模板—实现 Blueprint—合成案例”组织，而不是按原始来源或编程语言组织。

```text
agent-engineering-foundation/
├── docs/
├── frameworks/
├── skills/
├── templates/
├── blueprints/
├── examples/
├── pets/           # 可选的独立附加资源
├── packages/       # 未来按需
├── adapters/       # 未来按需
├── evals/          # 存在可使用 Skill 时按需
└── scripts/        # 存在确定性自动化时按需
```

目录不需要一次性全部创建。没有实际内容时不保留空目录。

`pets/` 可以与主体内容保存在同一仓库，但不参与 Agent 工程能力的依赖关系、成熟度评估或发布验收。

## `frameworks/`

存放 Markdown-first 的通用问题模型和契约草案：

```text
frameworks/
├── checkpoint/
├── evidence/
├── web-prefetch/
└── skill-eval/
```

每个框架重点说明：

- 解决的问题和不解决的问题；
- 核心对象、关系和状态；
- Agent、程序与人工的职责；
- 唯一事实来源和依赖方向；
- 合成应用案例；
- 未来工程化时可以采用的接口草案。

框架达到 `designed` 即可成为有效沉淀，不要求存在可运行 Package。

## `packages/`（未来按需）

只有实际复用需求出现后，才放可被多个能力复用的确定性参考实现。

可能的未来形态：

```text
packages/
├── checkpoint-core/
├── prefetch-core/
├── specflow-core/
├── skill-runtime/
├── evidence-core/
└── skill-eval-kit/
```

Package 应具备：

- 稳定的数据结构；
- 明确的公开接口；
- 不依赖特定公司的实现；
- 单元测试；
- 版本兼容说明。

Package 不负责理解业务意图，也不主动调用外部系统。

上述要求只约束真正创建的 Package，不是 Markdown 首版的验收条件。

`prefetch-core` 不只是类型定义。它负责首屏预请求领域内可以确定性表达和校验的规则：

```text
prefetch-core/
├── contracts/
├── readiness/
├── eligibility/
├── scheduling/
└── comparison/
```

- `contracts/`：页面场景、候选请求和结果的数据结构；
- `readiness/`：可见完成条件及其稳定性；
- `eligibility/`：副作用、幂等、鉴权、缓存 Key、降级和失效；
- `scheduling/`：依据上层明确提供的候选与策略执行校验、评分和排序；
- `comparison/`：行为结果与性能结果的结构化比较。

`prefetch-core` 不负责猜测用户真正关心的首屏终点，也不自行选择要修改的请求。候选选择、风险权衡和实现范围由上层 Skill 或人工完成。

Checkpoint 和 Evidence 是横向共享框架，不属于某一个上层 Skill。未来如果形成 Core Package，继续遵循同一边界：

```text
checkpoint-core
├── web-first-screen-prefetch
├── specflow 的执行恢复层（可选）
└── 未来的 D2C、迁移和审计能力

evidence-core
├── web-first-screen-prefetch
├── web-performance-review
└── 未来的覆盖率、Review 和审计能力
```

二者的对象所有权和依赖方向固定如下：

| 对象或职责 | 唯一所有者 | 说明 |
| --- | --- | --- |
| Evidence | `evidence-core` | 可验证的原始观察及来源、范围、时间、内容摘要 |
| Claim | `evidence-core` | 观察、程序推导或 Agent 推断形成的主张 |
| Blocker | `evidence-core` | 缺失或失效证据对特定 Claim 的阻断 |
| Verification | `evidence-core` | 证实或证伪 Claim 的动作与结果 |
| Run、Stage、Event | `checkpoint-core` | 一次长任务执行过程及其恢复位置 |
| Decision | `checkpoint-core` | 人工或策略作出的执行决策 |
| ExternalRef | `checkpoint-core` | 对 Evidence、Claim、文件或外部产物的不透明引用 |
| 阶段退出 | 组合 Validator | 同时读取 Checkpoint 状态和 Evidence 校验结果，不在任一 Core 中复制另一方数据 |

依赖规则：

- `evidence-core` 不依赖 `checkpoint-core`；
- `checkpoint-core` 通过通用 `ExternalRef` 保存引用，不复制 Evidence 或 Claim；
- 上层 Skill 或组合 Validator 负责调用两个 Core；
- Claim 过期由 `evidence-core` 判定，Checkpoint 只追加相应事件并阻止阶段错误退出。

`specflow-core` 与 Checkpoint 的状态所有权也必须保持单一：

- `specflow-core/meta` 是需求、计划和任务生命周期的唯一事实来源；
- Checkpoint 只保存某次 Agent 执行 Specflow 工作时的恢复位置；
- Checkpoint 不镜像 Draft、Planned、In Progress、Archived 等状态；
- Specflow 第一版可以不依赖 Checkpoint，只有长任务恢复场景需要时才接入。

## `skills/`

放面向 Agent 的能力编排。

首批规划：

```text
skills/
├── web-first-screen-prefetch/
└── web-performance-review/
```

每个 Skill 至少包含：

```text
skill-name/
├── SKILL.md
├── references/
├── assets/
├── evals/
└── agents/
```

如果存在确定性脚本，再增加 `scripts/` 和对应 `tests/`。

首期只要求两个可使用 Skill。Skill 能够指导 Agent 稳定执行即可，不要求附带程序代码。每个 Skill 必须按照[能力说明模板](04-能力说明模板.md)完成边界、输入输出、资源和行为 Eval 设计。

## `templates/`

存放可以被其他个人或项目直接复制修改的产物：

```text
templates/
├── specflow/
├── skill-runtime/
├── skill-eval/
├── ai-friendly-repository/
└── reports/
```

模板需要说明适用场景、必填字段和最小示例，但不要求存在生成器。

## `adapters/`（未来按需）

只有需要提供可运行参考实现时，才使用 Adapter 对接外部环境：

```text
adapters/
├── browser/
├── source-control/
├── version-evidence/
├── work-item/
└── mock/
```

核心模块只认识接口，例如：

```ts
interface BrowserProvider {
  captureNetwork(): Promise<NetworkEvidence>;
  captureDom(): Promise<DomEvidence>;
}
```

不同使用方可以实现 Chrome、Playwright、远程浏览器或自己的测试环境 Adapter。Markdown 首版只需要保留能力边界和接口示例。

`version-evidence/` 只负责证明分析、实现、制品和运行页面之间的版本关系，不负责触发部署：

```text
version-evidence/
├── git/
├── build-manifest/
├── deployment-metadata/
└── manual-confirmation/
```

如果无法建立版本映射，Adapter 应返回明确的证据等级和限制，上层 Skill 据此收窄结论。

## `blueprints/`

存放暂时无法提供完整通用实现的能力。

Blueprint 不是零散想法，必须包含：

- 问题与适用范围；
- 数据流；
- 核心契约；
- Agent 与程序的分工；
- 扩展点；
- 安全边界；
- 失败模式；
- 生产化缺口。

当前已经落地：

```text
blueprints/
├── specflow/
└── skill-runtime/
```

设计稿到代码、埋点生成、Agent 遥测和发布编排可以在完成同等边界设计后放在这里。

## `examples/`

Example 只使用自行创建的合成场景，可能包括：

- 一个 Web 场景说明，未来可选增加小型 Demo；
- 一个虚构需求，用于演示 Specflow；
- 一个自定义 Skill Case，用于演示触发、调用和 Eval。

Example 的目标是解释模块如何组合，不要求全部可运行，也不复刻真实业务。

## `evals/`

存放可使用 Skill 的 Agent 行为评估，以及确有必要的跨 Skill 案例：

- 触发是否准确；
- 是否混淆证据和推断；
- 缺少证据时是否夸大结论；
- 是否越过人工确认；
- 恢复时是否重复执行；
- 状态变化后是否发现旧结论过期。

纯框架和 Blueprint 只需要合成案例走查，不要求自动化 Eval。单元测试只在出现确定性程序时增加。

## `docs/`

存放：

- 总体架构；
- 能力地图；
- 扩展指南；
- Skill 编写规范；
- 安全和隐私规范；
- 公开来源说明。

## `scripts/`（未来按需）

只在确实存在需要重复自动化的确定性动作时增加，例如：

- 校验 Skill 目录；
- 校验 Schema；
- 扫描敏感标识；
- 运行 Eval；
- 检查示例是否可运行。

首期发布前的敏感信息检查可以人工执行或使用临时命令，不要求仓库先建设扫描工具。
