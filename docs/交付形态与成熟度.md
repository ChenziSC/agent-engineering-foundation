# 交付形态与成熟度

## 交付形态

| 形态 | 主要内容 | 是否必须可运行 |
| --- | --- | --- |
| 设计框架 | 问题模型、对象、边界、状态、决策规则和失败模式 | 否 |
| Blueprint | 数据流、契约、扩展点、安全边界和生产化缺口 | 否 |
| Template / Asset | 可复制修改的 Markdown、YAML 或 JSON 骨架 | 否 |
| 可使用 Skill | `SKILL.md`、References、Assets 和行为案例 | Agent 必须能按说明执行，不要求附带代码 |
| Starter | 可复制或初始化的最小项目骨架 | 是 |
| 参考实现 | Package、CLI、Adapter、Script 和 Test | 是 |

Markdown-first 表示设计原因和契约是一等产物，不表示仓库永远不提供代码。确定性实现只有在可以降低错误、稳定复用或形成机器门禁时才增加。

## 成熟度标记

| 标记 | 含义 |
| --- | --- |
| `idea` | 已确认问题价值，但边界和交付尚未完整设计 |
| `designed` | 问题、契约、职责、安全边界和合成案例已经明确 |
| `usable` | Skill、模板或 Starter 可以被其他项目实际采用 |
| `reference-implemented` | 已提供有测试的可运行参考实现 |
| `validated` | 需要 Agent 或人工语义判断的行为资产已通过正式回放，并保存可复核证据 |

成熟度描述具体资产，不自动向整个能力传播，也不把确定性实现的程序测试重复标成 `validated`。例如 Specflow Skill 可以通过正式回放达到 `validated`，本地双终态事项关系事务是有测试的 `reference-implemented`，Active 事项关系事务、三个及以上事项关系事务和跨仓库关系事务仍是 `designed`。

## 成熟度门禁

### 升级为 `designed`

- 问题、非目标、输入输出和对象所有权明确；
- Agent、程序和人工职责分开；
- 安全边界、失败模式和合成案例完整；
- 公开等级、通用性、内部信息移除情况和具体表达/实现的复用依据已记录。

### 升级为 `usable`

- Skill 或模板有明确触发、步骤和输出；
- 链接、YAML/JSON 和目录结构通过检查；
- 使用方不依赖受限平台即可执行核心流程；
- 未实现的程序能力不会被写成必然存在。

### 升级为 `reference-implemented`

- 可运行代码和公开接口实际存在；
- 失败不会留下不一致或半写入状态；
- 有单元或端到端测试；
- 版本、依赖和兼容边界明确。

### 升级为 `validated`

- Skill 或其他需要语义判断的行为资产具有正式回放及保存的证据；
- 验证使用的模型和推理强度由调用时环境选择，不写死在仓库契约中；
- 验证范围和未覆盖内容保持可见。

确定性脚本、CLI、Validator 或 Adapter 通过自动化测试后仍标记为 `reference-implemented`；测试是该标记的准入条件，不另行把同一资产升为 `validated`。

## 工程化判断

满足以下任一条件时，才把设计资产升级为实现：

- 人工步骤频繁出错，程序可以显著降低风险；
- 需要机器校验稳定 Schema、状态机或安全门禁；
- 已出现多个使用方需要同一确定性能力；
- 实现本身能形成跨项目的最小纵向闭环。

不要为了目录完整创建空 Package、Script、Test 或 Adapter。

新增能力还必须说明宿主已有基线、增量缺口、直接消费者和删除条件；只重述通用 Agent 行为或 Host 原生 Runtime 能力时，不进入实现。
