# 能力地图

## 目的

本页给出仓库的能力分层、建设优先级和依赖方向。33 项通用问题、公开等级和细粒度缺口见[能力问题图谱](能力问题图谱.md)。

迁移成本不作为主要排序因素。优先级主要看：

- 是否是其他能力的共同底座；
- 是否决定项目能否快速、可靠接入；
- 是否具有稳定契约和确定性验证价值；
- 是否能在没有私有平台的环境中工作；
- 是否已经有真实问题和失败模式支撑设计。

## 三层能力

| 层级 | 解决的问题 | 当前主要产物 | 当前状态 |
| --- | --- | --- | --- |
| 设计原因与长期知识 | 为什么存在、边界和不变量是什么 | `frameworks/`、`knowledge/` | 已有有效资产 |
| 项目采用与 Agent 执行 | 如何复制、配置和执行 | `skills/`、`templates/`、`blueprints/` | 可人工采用，部分 Skill 可直接执行 |
| 项目级治理接入内核 | 如何初始化、校验、持久化和接入项目事实 | `starter/`、`packages/harness/`、`adapters/` | 最小项目级闭环已参考实现并通过测试 |

三层资产共同构成通用的项目级 Agent Harness 化脚手架。其中“接入内核”只指可复用的确定性基础设施，不等于完整 Agent Runtime；项目专属知识、语言级工具链、真实运行沙箱、观测与审批发布能力仍由采用方配置或通过 Adapter 接入。

`docs/` 不构成第四层能力，也不拥有上述能力契约；它只为读者提供跨层导航、成熟度投影、发布检查和来源声明。

## 依赖方向

```text
AGENTS / Knowledge / Repository Context
├── Context Resolver
│   ├── Active Spec / Knowledge Route
│   └── Section Index
├── Repository Context Audit
│   └── Task-scoped Evidence View
├── Semantic Slice Candidate
│   └── Language Adapter / Field Dataflow / Risk Rules
├── Specflow
│   ├── Archive / Lifecycle / Context
│   └── Knowledge Projection / Change Gate
├── Skill Source / Native Host Distribution
│   └── Skill Eval
├── Evidence
│   ├── Web 首屏预请求
│   ├── Web 性能评审
│   └── 增量覆盖、浏览器验证、D2C、埋点与安全变更
└── Starter / Harness / Doctor
    ├── 初始化与安装更新
    └── 结构、引用、Schema 和发布门禁

External-effect Receipt
└── 只在采用方需要跨进程幂等恢复时使用
```

## 唯一事实来源

- Specflow Meta 只管理研发事项生命周期；Checkpoint 不镜像该状态；
- Evidence、Claim、Blocker 和 Verification 只在 Evidence 模型定义；
- Knowledge 保存长期事实，Specflow 保存当前事项，README 只做入口；
- Context Contract 只定义上下文层级、所有权和来源边界；稳定正文由 Knowledge 拥有，任务调研由当前 Spec 拥有；
- Skill 的触发和编排只在 Skill 源目录维护，安装与更新优先由 Agent Host 原生机制负责；
- 外部浏览器、版本证据、工作项和代码托管平台统一通过 Adapter 接入；
- 项目组件治理只定义一次，D2C 和组件测试消费其决策，不复制准入规则。

## 项目级 Harness 化接入内核当前边界

当前参考实现已经通过完全合成的临时项目测试，覆盖：

1. 可以在临时项目初始化 Starter；
2. 可以发现并检查本仓 Skill；
3. 安装和更新前给出计划，冲突时停止；
4. 至少支持一个项目级兼容 Skill 目录；
5. Doctor 能检查 Starter 契约、Knowledge Registry/Code Entry Map、权威来源摘要和受管 Skill 完整性；
6. 重复执行幂等，失败不留下半安装状态；
7. 具备完全合成的端到端测试；
8. 已有项目可先生成只读接入计划，且父路径或目标中的 Symlink 会在写入前阻断；
9. Skill 检查从真实目录动态发现，不依赖固定名称或数量。
10. Change Gate 对完整 Merge Candidate 强制一个或多个 Spec 的显式集合关联与 Scope 并集覆盖，或者使用受控路径型豁免，并可在交付阶段逐项复核 Receipt 与 Lifecycle 证据。
11. Context 按请求路径自动加载祖先规则；Doctor 检查规则文件预算、失效入口、结构性路由矛盾和父子规则精确重复。
12. `specflow check` 校验完整 Meta、产物、本地关系和终态证据链。
13. Distribution Manifest 支持项目级兼容 Plan/Apply/Verify，并以内容摘要固定全部可发布 Skill。
14. Evidence Bundle、Checkpoint、增量验证、[Web Evidence](../frameworks/web-evidence/README.md)、Design Contract、Event Catalog、Skill Eval Runner/Scorer 和组件 Registry Validator 均有零依赖参考实现与测试。

仓库级检查另行覆盖真实目录、JSON/JSON Schema、当前 YAML 子集、Markdown 链接、Skill/Eval Replay、Distribution Manifest、Knowledge 索引与来源摘要、高置信秘密格式、无扩展名文本和路径；按显式参数还可检查暂存区、Git 历史、Reflog 与不可达对象。Projection 更新器只机械维护 Registry，不生成正文或替代语义判断。Doctor 只识别精确重复和结构性矛盾，不推断自然语言规则冲突。Change Gate 不自行创建不可变候选，也不替代终态授权或外部平台检查。Relation Transaction 只覆盖同一 Specs Root 下两个终态事项，不承诺跨文件绝对原子可见性。尚未覆盖 Active 事项关系事务、三个及以上事项关系事务、跨仓库关系事务、字段级 AST 切片、二进制语义、私有词表本身的维护和人工权属复核；这些内容不能由当前检查通过推断出来。
