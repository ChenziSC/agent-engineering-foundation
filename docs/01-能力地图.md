# 能力地图

## 目的

本页给出仓库的能力分层、建设优先级和依赖方向。30 项通用问题、公开等级和细粒度缺口见[能力问题图谱](08-能力问题图谱.md)。

迁移成本不作为主要排序因素。优先级主要看：

- 是否是其他能力的共同底座；
- 是否决定项目能否快速、可靠接入；
- 是否具有稳定契约和确定性验证价值；
- 是否能在没有私有平台的环境中工作；
- 是否已经有真实问题和失败模式支撑设计。

## 三层能力

| 层级 | 解决的问题 | 当前主要产物 | 当前状态 |
| --- | --- | --- | --- |
| 设计原因与长期知识 | 为什么存在、边界和不变量是什么 | `frameworks/`、`knowledge/`、`docs/` | 已有有效资产 |
| 项目采用与 Agent 执行 | 如何复制、配置和执行 | `skills/`、`templates/`、`blueprints/` | 可人工采用，部分 Skill 可直接执行 |
| 确定性 Harness | 如何初始化、安装、校验、持久化和接入宿主 | `starter/`、`packages/harness/`、`adapters/open-agent/` | 最小项目级闭环已参考实现并通过测试 |

## 治理底座建设优先级

该表回答“为了让任意项目快速接入，仓库接下来先建设什么”。它不等同于领域 Skill 的价值排名。

| 顺序 | 能力 | 优先级 | 当前成熟度 | 下一缺口 |
| ---: | --- | --- | --- | --- |
| 1 | Specflow 语义流程与归档契约 | P0 | Skill `usable`；归档契约 `designed` | 确定性摘要、Receipt/Event 写入与校验 |
| 2 | AI 友好仓库与 Knowledge 治理 | P0 | 模板 `usable`；最小 Starter/Doctor 与仓库检查 `reference-implemented` | Registry 语义与 Knowledge 新鲜度检查 |
| 3 | Skill 运行时与分发 | P0 | Blueprint `designed`；项目级 Host Registry `reference-implemented` | 分发 Manifest、用户级安装和更完整发布契约 |
| 4 | Evidence 与 Claim | P0 | `designed` | 供 Validator 和上层 Skill 复用的参考实现 |
| 5 | Skill 行为评估 | P0 | `usable` | 通用 Runner、Trace 和回归比较 |
| 6 | 长任务 Checkpoint | P0 | `designed` | 只有真实长任务复用时再实现通用内核 |
| 7 | 项目初始化与 Doctor | P0 | 最小范围 `reference-implemented` | Specflow 生命周期语义、Archive 与新鲜度校验 |
| 8 | 变更关联与发布门禁 | P1 | `designed` | 结构化低风险豁免、Merge Candidate 与公开检查 |

当前已完成默认开放 Host、可注入项目级 Host Registry、最小 Starter/Harness 闭环和仓库级静态质量门禁；不会实现或打包真实公司基建 Adapter。

## 已验证或可使用的领域能力

领域能力验证治理底座是否真正可用，不应被核心 Harness 强制安装。

| 能力 | 优先级 | 当前成熟度 | 定位 |
| --- | --- | --- | --- |
| Web 首屏预请求 | P0 | `validated` | 当前成熟度最高的通用领域 Skill，也是 Checkpoint 与 Evidence 的首个综合验证场景 |
| Web 性能评审 | P0 | `validated` | 验证多类输入证据、代码映射和受限结论 |
| 项目组件治理与维护 | P1 | `usable` | 验证发现、放置、准入、迁移和废弃的项目治理流程 |

Web 首屏预请求仍是仓库中最通用、最成熟的领域 Skill；治理底座排在实现顺序前面，是因为它决定其他项目如何安装、验证和持续维护这些 Skill，而不是降低该能力本身的价值。

## 依赖方向

```text
AGENTS / Knowledge / Repository Context
├── Specflow
│   ├── Archive / Lifecycle / Context
│   └── Knowledge Projection / Change Gate
├── Skill Runtime
│   ├── Capability Registry
│   └── Skill Eval
├── Evidence
│   ├── Web 首屏预请求
│   ├── Web 性能评审
│   └── 未来覆盖率、浏览器验证、D2C 与安全变更
└── Starter / Harness / Doctor
    ├── 初始化与安装更新
    └── 结构、引用、Schema 和发布门禁

Checkpoint
├── Web 首屏预请求
├── Specflow 长任务恢复（可选）
└── 未来 D2C、迁移和审计
```

## 唯一事实来源

- Specflow Meta 只管理研发事项生命周期；Checkpoint 不镜像该状态；
- Evidence、Claim、Blocker 和 Verification 只在 Evidence 模型定义；
- Knowledge 保存长期事实，Specflow 保存当前事项，README 只做入口；
- Skill 的触发和编排只在 Skill 源目录维护，安装目录是运行副本；
- 外部浏览器、版本证据、工作项和代码托管平台统一通过 Adapter 接入；
- 项目组件治理只定义一次，D2C 和组件测试消费其决策，不复制准入规则。

## 最小 Harness 当前边界

当前参考实现已经通过完全合成的临时项目测试，覆盖：

1. 可以在临时项目初始化 Starter；
2. 可以发现并检查本仓 Skill；
3. 安装和更新前给出计划，冲突时停止；
4. 至少支持一个开放 Host 目录；
5. Doctor 能检查 Starter 契约、Knowledge 空索引结构和受管 Skill 完整性；
6. 重复执行幂等，失败不留下半安装状态；
7. 具备完全合成的端到端测试。

仓库级检查另行覆盖真实目录、JSON/JSON Schema、当前 YAML 子集、Markdown 链接、Skill/Eval 结构和高置信秘密格式。尚未覆盖 Specflow 生命周期语义、Knowledge 新鲜度、分发 Manifest、用户级安装、私有词表本身的维护和人工权属复核；这些内容不能由当前检查通过推断出来。
