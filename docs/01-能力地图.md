# 能力地图

## 排序原则

迁移成本不作为主要考虑因素。排序主要看：

- 能否成为其他项目的基础设施；
- 能否支撑多个上层场景；
- 是否具备稳定的输入输出和状态模型；
- 是否能够通过程序或 Eval 验证；
- 是否具有长期扩展价值。

## 能力之间的关系

```text
AI 友好仓库
├── Skill 运行时与分发
│   └── Skill 行为评估
├── Spec 驱动研发流程
├── 项目组件治理与维护
├── Web 首屏预请求
└── Web 性能评审

共享底座
├── 长任务 Checkpoint
│   ├── Spec 驱动研发流程的执行恢复层（可选）
│   ├── Web 首屏预请求
│   └── 未来的 D2C、迁移和审计能力
└── 证据与推断模型
    ├── Web 性能评审
    ├── Web 首屏预请求
    └── 未来的覆盖率、Review 和审计能力
```

这个关系不是调用关系的全部，也不表示第一阶段要同时实现八套程序：

- 仓库规范提供上下文；
- Skill Runtime Blueprint 说明发现和分发边界；
- Eval 方法论负责描述质量；
- Specflow 是研发事项生命周期的唯一事实来源；
- Checkpoint 作为横向底座，只负责单次长任务执行的状态和恢复；
- Evidence Core 负责可信结论；
- 两个 Web 能力负责验证底座是否真的可用。

## 沉淀顺序

沉淀顺序按知识依赖关系组织，不和价值优先级强行保持一致，也不默认进入代码实现。

### 阶段 A：冻结最小共享概念

1. 定义 Evidence、Claim、Blocker 和 Verification；
2. 定义 Run、Stage、Event、Decision 和通用外部引用；
3. 明确 Evidence 不依赖 Checkpoint，Checkpoint 不复制 Evidence 内容；
4. 用 Schema 示例和合成案例走查二者如何组合。

### 阶段 B：完成第一个可使用 Skill

1. 沉淀首屏预请求的问题模型、就绪条件、资格校验和比较规则；
2. 编写 `web-first-screen-prefetch` Skill；
3. 提供分析报告和验证清单模板；
4. 使用完全合成的案例做行为 Eval；
5. 把 Validator、Mock Adapter 和可运行 Demo 保留为可选参考实现。

阶段 B 的完成标准是 Agent 能依据 Skill 和模板完成合成案例，并遵守安全与证据边界，而不是所有通用 Package 都已经实现。

### 阶段 C：沉淀复用模板和 Blueprint

1. 从首个 Skill 中抽取 Eval Case 和 Rubric 模板；
2. 编写 Skill 运行时与分发 Blueprint；
3. 建立 AI 友好仓库模板和检查清单；
4. 不要求同步实现 Runner、CLI 或 Health Check。

### 阶段 D：扩展其他 P0 沉淀

1. 提供 Specflow 生命周期 Blueprint 和 Markdown 模板；
2. 说明按需接入 Checkpoint 执行恢复层的方式；
3. 编写 Web 性能评审 Skill 并复用 Evidence 框架；
4. 用第二个、第三个场景检验共享概念是否确实通用。

## 可选工程化路径

当实际使用证明某个确定性能力值得实现时，再增加对应 Package、Adapter、脚本或测试。工程化顺序仍应遵守本页定义的依赖方向，但不属于 Markdown 首版的完成条件。

## 不重复建设

- Checkpoint 模型只定义一次，首屏预请求和后续长任务直接复用；未来如有参考实现，也只能有一个通用内核。
- Evidence、Claim、推断、置信度、阻塞项和验证结果只在证据模型中定义。
- Checkpoint 只记录运行事件和对 Evidence、Claim 的引用，不保存第二份证据或结论。
- Specflow 的 `meta` 是研发事项生命周期的唯一事实来源，Checkpoint 不镜像该状态。
- 可使用 Skill 的触发、输出和安全性统一使用同一套 Eval 方法；是否提供自动化工具另行决定。
- 项目组件治理只定义一次组件发现、放置、准入、迁移和废弃模型；设计稿到代码、组件测试和 Package 发布只消费其决策，不复制治理规则。
- 外部浏览器、版本证据、工作项和代码托管平台统一通过 Adapter 接入。
