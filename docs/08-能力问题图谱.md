# 能力问题图谱

## 目的

本图谱回答“跨项目的 Agent 工程实际需要解决哪些问题”，而不是复刻任何来源仓库的文件结构。它由非公开覆盖台账投影而来，只保留通用问题、公开处理等级、当前资产和缺口，不包含来源路径、内部平台、真实案例或实现细节。

## 阅读方式

- 优先级表示对“任意项目快速接入 Agent 工程治理骨架”的价值，不表示必须同时编码；
- 公开等级表示允许沉淀的深度，仍需独立设计和发布前复核；
- 成熟度沿用[交付形态与成熟度](05-交付形态与成熟度.md)；
- `idea` 也是有效盘点结论，但不能写成已经可用。

## 当前主要缺口

### P0：让治理骨架真正可接入

1. Specflow 的确定性归档、Lifecycle、Context 和 Knowledge Projection；
2. Repository Doctor 的唯一来源、上下文体量和新鲜度语义；
3. 事项与变更关联、结构化低风险豁免和失败保持不变门禁。

### P1：形成第二组可验证闭环

1. Knowledge Registry、新鲜度和代码反向命中；
2. 增量覆盖证据与浏览器验证；
3. 安全变更状态机；
4. D2C 和埋点的 Spec 投影流水线；
5. 差异感知质量门禁与 Repository Doctor 合并验证。

### P2：等待真实公开使用方

发布平台、需求系统、工作台账、领域查询、远端度量和多宿主 Hook 都有真实价值，但首版应先保留 Provider/Adapter、状态机和隐私边界，不默认绑定或实现某个外部平台。

## 依赖方向

```text
仓库上下文与 Knowledge
├── Specflow
│   ├── Archive / Lifecycle / Context
│   └── Change Gate / Knowledge Projection
├── Skill Runtime
│   ├── Capability Registry
│   └── Skill Eval
├── Evidence
│   ├── 覆盖率与浏览器验证
│   ├── Web 性能与首屏预请求
│   └── D2C、埋点与安全变更
└── Harness / Doctor
    ├── 项目初始化与安装更新
    └── 结构、引用、Schema 和发布门禁
```

后续新增能力时，先在本图谱中确认它解决的是新问题还是已有能力的具体场景，避免为每个来源 Skill 创建一套重复底座。
