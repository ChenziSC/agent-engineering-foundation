# Spec：补齐渐进式项目规则就绪评估

## 背景

真实采用复核证明，项目可以同时具备完整 Skill 安装、Knowledge、代码入口和通用治理规则，却仍缺少项目心智模型、本地开发方法、明确验证入口或项目特有红线。当前 Bootstrap 能列出规则候选，但报告没有独立的规则就绪度视图，容易把“治理文件存在”误写成“Agent 已足以开发该项目”。

## 目标

- 让 Bootstrap 独立评估项目规则是否回答“项目是什么、从哪里修改、怎样开发与验证”；
- 区分仓库可观察事实、Agent 推断和必须由维护者确认的项目约定；
- 按首次接入、任务触发和项目成熟三个阶段引导采用方增量完善，不在首次接入制造大问卷、空配置或过长根规则；
- 用行为案例阻断仅凭 AGENTS、Knowledge、Doctor 或完整 Skill 安装判定项目规则已经就绪。

## 非目标

- 不把任何真实采用项目的业务、平台、目录、命令或内部规则写入公共资产；
- 不建立项目规则 Schema、Capability Registry、持久化状态或新的 Harness CLI；
- 不要求所有项目拥有模块级 AGENTS、分支规范、组件 Registry 或外部 Adapter；
- 不让 Bootstrap 自动批准或写入目标项目；
- 不把语义评估伪装成确定性程序证明。

## 行为契约

项目规则就绪度与 Skill 就绪矩阵分开表达。至少评估以下维度：

1. 项目心智模型与主要流程；
2. 架构边界与任务路由；
3. 工具链、依赖安装和本地开发入口；
4. 按变更类型适用的构建、测试、静态检查和人工验证；
5. 跨仓库、外部服务、配置和敏感信息边界；
6. 项目特有且有维护者依据的禁止事项；
7. 是否存在需要模块级规则的密集稳定模式；
8. 目标 Agent Host 的规则入口或薄桥接需求。

每一维使用 `ready`、`needs-project-config`、`not-applicable` 或 `unresolved`，同时记录 Evidence、观察层级、缺口、建议位置、完善阶段和是否需要维护者回答。`ready` 只表示完成当前项目适用的最低规则基线，不表示所有可选领域都已配置。

## 完成条件

- **AC-001** Skill 明确项目规则就绪度与 Skill 就绪矩阵的职责差异；
- **AC-002** 报告模板覆盖八类规则维度、状态、Evidence、落点、完善阶段和维护者问题；
- **AC-003** 工作流定义首次接入、任务触发、项目成熟三个渐进阶段，并保持根规则、Knowledge、模块规则、领域配置和当前 Spec 的所有权边界；
- **AC-004** 首次接入只要求项目适用的最低可开发基线，不预建空 Registry、Adapter、模块规则或项目制度；
- **AC-005** 新增反例行为 Case：治理文件和完整 Skill 均存在但根规则仍过于通用时，必须识别缺口；
- **AC-006** Eval Rubric 阻断仅凭文件存在、Doctor 或 Skill 安装宣称项目规则完整；
- **AC-007** Docs、行为案例数量和 Distribution 内容摘要与实现一致；
- **AC-008** Skill Check、Repository Check、全量测试、Specflow、Knowledge 与敏感扫描通过；
- **AC-009** 公共变更不包含真实采用项目或受限来源的具体信息；
- **AC-010** 在一个已完成 Harness 接入的真实项目上执行当前 Skill：先只读识别规则语义缺口，在获得写入授权后更新受管 Skill 并生成可追溯候选；维护者问题收敛到最低开发基线，未确认推断不进入长期事实。
