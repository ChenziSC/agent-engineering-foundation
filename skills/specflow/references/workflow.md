# 工作流与退出条件

## 1. 恢复或建立事项

先搜索非终态 Meta，并按影响范围、标题和关系选择相关事项。找到相关事项时继续维护，不新建重复目录；没有相关事项且请求需要长期产物时，创建新的事项目录。

退出条件：事项身份唯一，输入来源和影响范围可追溯。

## 2. 建立 Spec

把输入转化为目标、非目标、用户场景、行为契约和完成条件。只询问会改变范围、验收或高风险行为的问题；非阻塞未知记录为 Assumption。

退出条件：范围闭合，重大歧义为零，每个目标至少有一个可判断的完成条件。

## 3. 建立 Plan

先读取真实实现证据，再说明数据流、组件职责、兼容性、备选决策、测试策略和回退方式。判断改变的是产品行为、稳定契约、技术路径、局部实现还是纯验证，列出不能猜测的不变量、允许依赖的事实和需要的 Evidence 来源关系。重大未知才建立限时 Research。

退出条件：关键决策有证据或明确假设；完成条件有实现和验证路径。

## 4. 生成 Tasks

按依赖顺序拆解可独立完成的工作。每项任务写明输入、动作、产物、对应章节和验证方式。

退出条件：没有孤立完成条件，没有无法验证的任务，依赖关系明确。

## 5. 实施与验证

只有用户要求实现时才修改代码。持续运行最小相关检查；完成后再执行风险匹配的整体验证。按以下规则回流：

| 发现的变化 | 回流位置 |
| --- | --- |
| 目标、范围、用户行为或完成条件变化 | Spec |
| 公共契约、Schema、不变量、兼容或回滚策略变化 | Plan，并按需同步 Spec |
| 关键技术路径或影响范围变化 | Plan |
| 局部实现、任务拆分或纯验证变化 | Tasks，必要时补充 Plan 的验证部分 |
| Evidence 与设计冲突 | 保持 Active，回到支持该主张的 Spec 或 Plan |

同一设计的复述和自生成清单不能作为唯一正确性证据；记录测试执行、运行观察、静态契约检查或人工 Review 的候选版本、范围和来源关系。

退出条件：实现与最终 Spec、Plan、Tasks 一致；每个完成条件都有证据，未完成项保持可见。

## 6. 收口与交付

收口前回读最终代码和测试结果，更新过期产物并生成 Validation Report。只有存在明确终态授权时，才按 [archive-and-lifecycle.md](archive-and-lifecycle.md) 生成并回读 Receipt、完成 Knowledge Projection，并最后更新 Meta。PR/MR、提交、推送或外部工作项操作是独立动作，不由终态自动触发。

退出条件：状态合法，关系一致，Receipt/Event 链和 Knowledge Projection 可复核，Blocker 不被隐藏；对外部交付只声明实际完成的动作。缺少确定性摘要条件时保持 Active。
