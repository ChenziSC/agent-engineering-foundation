# 输入与证据边界

## 通用输入

以下内容都可以作为产品或研发输入：

- PRD 或其他需求文档；
- Figma 或其他设计稿；
- GitHub Issue、GitLab Issue 或其他工作项；
- 评审纪要、用户反馈和缺陷描述；
- 自然语言目标；
- 已有 Meta 及其声明的 Spec、Plan、Tasks 等产物。

PRD 是文档类型，Figma 是公开的第三方设计平台。二者无需因公开沉淀而删除。需要隔离的是特定组织的空间、账号、链接、项目标识、权限流程和专用字段。

## 证据优先级

按任务需要读取：

1. 用户明确提供的目标、约束和授权；
2. 当前版本的代码、测试、配置和公开契约；
3. 可访问的需求或设计原文；
4. 版本历史、Issue、PR/MR 和 CI 结果；
5. Agent 推断。

前四类也可能冲突或过期。记录来源、时间和适用版本，不仅记录链接。Agent 推断必须标为 Assumption，不得伪装成仓库事实。

## Evidence 来源关系

- `同源说明`：来自待验证设计本身的文字、自生成清单或没有外部观察的 Agent 复述，只能说明意图，不能独立证明正确性；
- `执行观察`：测试、构建、静态检查或运行时观察在明确候选版本上产生的结果，可以证明其实际覆盖范围内的行为；
- `交叉验证`：不同消费者、验证机制、运行场景或独立 Review 对同一主张提供补充证据，用于降低单一设计和单一测试渠道的共同盲区。

不要机械要求所有低风险变化都有多种验证渠道。涉及公共契约、不变量、权限、数据、兼容、不可逆变化或高影响回滚时，至少说明为什么现有执行观察足够，或增加与主要实现路径不同的交叉验证。Evidence 的引用、状态和冲突仍由项目的 Evidence 模型统一管理。

## Provider-neutral 规则

- 使用“工作项”“设计稿”“代码托管变更”等通用概念描述流程。
- 允许记录实际使用的 GitHub、GitLab、Figma 等公开 Provider，但核心状态不依赖它们。
- 外部链接失效时，保留完成任务所需的最小摘要；不要复制无关全文。
- 不把外部工作项状态作为 `meta.yaml` 生命周期的第二事实来源。

## 信息不足

缺少目标仓库时，可以整理需求但不能给出代码级 Plan。缺少完成条件时保持 Draft。缺少外部平台权限时，生成交付草案并明确说明未执行外部动作。
