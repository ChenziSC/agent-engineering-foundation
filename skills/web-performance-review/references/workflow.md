# 性能评审工作流

## 目录

1. 固定范围
2. 建立 Evidence 清单
3. 生成指标摘要
4. 识别瓶颈
5. 建立 Claim
6. 映射代码
7. 排序建议
8. 设计验证

## 1. 固定范围

记录：

- 页面和入口；
- 用户操作流程；
- 设备和浏览器；
- 网络条件；
- 冷缓存或热缓存；
- 登录、权限、语言和区域；
- 页面与代码版本。

不同条件下的结果不能直接放进同一基线。

退出条件：另一位执行者能够理解测量针对什么场景。

## 2. 建立 Evidence 清单

为每份输入记录：

- 来源；
- 采集时间；
- 范围；
- 版本；
- 内容摘要；
- 能观察什么；
- 不能观察什么。

读取 [evidence-by-input.md](evidence-by-input.md)，不要超出输入能力。

退出条件：所有后续指标和 Claim 都可以引用 Evidence ID。

## 3. 生成指标摘要

只报告当前材料可以支持的指标，例如：

- 导航和资源时序；
- LCP、CLS、INP 或实验室近似指标；
- 长任务；
- JavaScript 执行与样式布局；
- 请求数量、体积和缓存；
- 关键资源瀑布。

区分：

- 浏览器直接观察；
- 确定性计算；
- Agent 解释。

退出条件：指标没有脱离场景、版本和输入范围。

## 4. 识别瓶颈

读取 [bottleneck-taxonomy.md](bottleneck-taxonomy.md)，按影响用户终点的路径组织，而不是按工具面板顺序罗列。

优先回答：

1. 用户在等待什么；
2. 哪个阶段占用主要时间；
3. 哪些工作是串行的；
4. 哪些工作可以减少、延后或并行；
5. 哪些只是伴随发生，没有因果证据。

退出条件：每个高优先级瓶颈都指向一个用户可感知终点。

## 5. 建立 Claim

每个根因 Claim 包含：

- 主张；
- 类型：Observation、Derived 或 Inference；
- Evidence 引用；
- 适用范围；
- 置信度；
- 反证；
- 最短 Verification。

无法建立因果关系时，使用“候选原因”而不是“根因”。

退出条件：没有无引用的事实声明。

## 6. 映射代码

只有提供代码仓库时执行。读取 [code-mapping.md](code-mapping.md)。

优先检查：

- 路由和入口；
- 同步 Import；
- 初始化顺序；
- 数据请求触发；
- 渲染关键资源；
- 第三方脚本；
- 构建和缓存策略；
- 微前端容器与远程模块边界。

退出条件：代码位置是 Evidence 支持的候选，不是根据常见模式虚构的路径。

## 7. 排序建议

每条建议评估：

- 预期收益；
- Evidence 强度；
- 行为风险；
- 改动范围；
- 验证成本；
- 依赖和阻塞。

高收益但证据弱的建议可以列出，但不能排在“立即实施”类别。

## 8. 设计验证

行为验证：

- 页面主要流程；
- 空态、错误和权限；
- 导航与交互；
- 兼容和回退。

性能验证：

- 使用相同场景；
- 固定设备、网络和缓存；
- 保留版本映射；
- 使用多次测量而不是单次最好结果；
- 同时比较指标和用户可见终点。

退出条件：每项建议都有可以证实或证伪它的验证动作。
