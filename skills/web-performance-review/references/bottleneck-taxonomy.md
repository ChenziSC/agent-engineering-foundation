# Web 性能瓶颈分类

## 网络瀑布

线索：

- 关键请求等待前置请求；
- 重定向；
- 连接重复建立；
- 请求触发晚；
- 资源优先级不合理。

需要进一步证明请求与用户终点的关系。

## 资源体积

线索：

- JavaScript、CSS、图片或字体过大；
- 未使用资源；
- 压缩或格式不合适；
- 同一资源重复下载。

不要只按文件大小排序；同时考虑是否位于关键路径。

## JavaScript 与主线程

线索：

- 长任务；
- 大量解析、编译和执行；
- 同步初始化；
- 重复计算；
- 水合或渲染工作集中。

只有 HAR 时不能得出这一类结论。

## 样式、布局与绘制

线索：

- 频繁样式重算或布局；
- 大面积绘制；
- 布局抖动；
- 动画和视觉效果成本；
- 关键元素尺寸不稳定。

需要 Trace 或等价渲染 Evidence。

## 缓存

线索：

- 静态资源没有有效缓存；
- 内容摘要与缓存策略不一致；
- 缓存 Key 过粗或过细；
- 重复导航重新下载稳定资源。

不要在没有 Header 或配置 Evidence 时断言缓存配置错误。

## 第三方脚本

线索：

- 同步加载；
- 主线程长任务；
- 网络竞争；
- 初始化早于实际需要；
- 错误或超时拖慢主流程。

建议应同时考虑业务必要性、延后方式和失败隔离。

## 架构和加载边界

线索：

- 路由入口同步加载大量模块；
- 微前端容器先串行加载远程资源；
- 共享依赖重复；
- 初始化责任分散；
- 构建切分和运行边界不一致。

共享模块 Evidence 不能自动扩大成每个页面事实。

## 交互性能

线索：

- 事件处理耗时；
- 更新范围过大；
- 状态传播或重复渲染；
- 长任务阻塞输入响应；
- 动画与交互竞争主线程。

只分析页面加载时不能声称已经覆盖交互性能。

## 优先级

优先处理：

1. 与用户终点直接相关；
2. Evidence 较强；
3. 预期收益明确；
4. 行为风险可控；
5. 验证成本合理。
