# 不同输入的 Evidence 边界

## URL

如果当前环境可以访问并采集，可以获得浏览器现场 Evidence。记录登录、权限、设备、网络和版本条件。

如果无法采集，URL 本身不能证明性能状态。

## Lighthouse

适合：

- 实验室场景指标；
- 机会项线索；
- 资源摘要；
- 部分诊断信息。

限制：

- 不等同于真实用户数据；
- 单次分数容易波动；
- 机会项不是代码根因；
- 报告环境可能和目标用户不同。

## Performance Trace

适合：

- 主线程任务；
- JavaScript 执行；
- 样式、布局和绘制；
- 网络与渲染时序；
- 用户 Timing；
- 长任务和交互过程。

限制：

- 必须知道录制场景；
- Trace 本身不一定包含代码版本；
- 时间接近不自动构成因果关系。

## HAR

适合：

- 请求瀑布；
- DNS、连接、等待和下载时序；
- 请求数量和体积；
- Header 与缓存线索；
- 重定向。

限制：

- 不能证明主线程成本；
- 不能证明 DOM 或关键内容何时可见；
- 可能缺少完整 Body 或敏感 Header；
- 不能单独证明某请求阻塞渲染。

公开仓库不要保存真实 HAR。

## 代码仓库

适合：

- 找到入口、Import 和初始化路径；
- 检查请求触发与数据消费；
- 检查构建和缓存配置；
- 提出可验证的候选根因。

限制：

- 代码看起来会执行，不等于目标页面实际执行；
- 本地代码不一定对应采集页面；
- 没有运行 Evidence 时，结论仍是推断。

## 历史测量

适合趋势比较，但必须检查场景、设备、网络、缓存、版本和统计方式是否一致。

无法确认条件一致时，只作为背景，不直接计算提升比例。

## 版本 Evidence

从强到弱可能包括：

1. 页面、制品和代码的明确标识；
2. 构建清单；
3. 发布时间和人工确认；
4. 只有时间接近；
5. 无法映射。

时间接近只能作为线索，不能单独证明版本一致。
