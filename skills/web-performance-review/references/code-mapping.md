# 从性能 Evidence 映射到代码

## 原则

代码映射产生的是候选根因，不是自动成立的因果结论。

同时需要：

- 运行时 Evidence；
- 可定位的模块、资源或调用；
- 目标版本关系；
- 能证实或证伪的验证动作。

## 映射顺序

1. 从用户终点定位对应页面或功能。
2. 从 Trace、HAR 或资源名称找到运行时实体。
3. 在仓库中查找入口、Import、调用或配置。
4. 追踪到拥有该职责的最小模块。
5. 检查是否存在容器、共享层或构建转换。
6. 把代码位置记录为候选并说明证据强度。

## 常见入口

- 路由配置；
- 页面入口；
- 应用初始化；
- 数据请求封装与消费方；
- 同步 Import；
- 资源清单；
- 构建配置；
- 第三方脚本注入；
- 微前端容器和远程模块加载。

## 禁止做法

- 没有仓库时虚构文件路径；
- 根据框架习惯猜测真实入口；
- 看到相同文件名就认定是 Trace 中的资源；
- 忽略 Source Map、打包重命名或远程模块；
- 把共享模块成本全部归因于单页面；
- 未确认版本就声称代码已经在线运行。

## 输出强度

### 直接

运行资源可以映射到目标版本中的明确代码位置。

### 间接

资源名、调用或模块关系支持候选位置，但仍需实验验证。

### 未映射

只能描述运行症状，不能给出具体代码位置。

## 验证方式

- 暂时禁用或延后候选工作；
- 使用 Feature Flag；
- 增加 Timing 或性能标记；
- 对比构建产物；
- 使用 Source Map；
- 在相同场景重新采集 Trace；
- 控制单一变量。
