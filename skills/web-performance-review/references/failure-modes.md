# 常见失败模式

## 复述分数

问题：只罗列 Lighthouse 分数和机会项，没有解释用户等待路径。

修正：把指标映射到用户终点、瓶颈 Claim 和验证动作。

## 超出输入能力

问题：从 HAR 推断 JavaScript 长任务，从 Lighthouse 推断具体代码文件。

修正：按输入类型明确可观察和不可观察内容。

## 把相关性写成因果

问题：两个事件时间接近就认定其中一个导致另一个。

修正：使用“候选原因”，并设计控制变量的 Verification。

## 虚构代码根因

问题：没有仓库或版本映射却给出具体文件。

修正：只描述职责位置，或把代码映射标为 Blocker。

## 建议列表没有优先级

问题：输出大量常见优化，用户不知道先做什么。

修正：按收益、Evidence、风险、范围和验证成本排序。

## 用一次测量承诺收益

问题：把单次最好结果当成稳定改进。

修正：声明测量条件，进行多次一致场景比较。

## 忽略行为验证

问题：只关注性能指标，不检查错误、空态、权限和交互。

修正：每项改造同时设计行为和性能验证。

## 微前端范围扩大

问题：共享容器或远程模块 Evidence 被描述为某个页面的唯一根因。

修正：区分容器、共享依赖、远程模块和页面自身的范围。

## 与首屏预请求重复

问题：性能评审直接进入请求资格和预请求实现细节。

修正：先完成通用诊断；问题收敛后转用专项 Skill。
