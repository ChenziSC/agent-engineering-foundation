## Case 01

### W01-A｜实际决策、边界、产出和状态

- 状态：`complete`，仅限所提供的合成 Trace 场景。
- 事实：
  - Trace 观察到关键内容出现前存在约 420ms 的主线程同步初始化。
  - 关键数据请求与该初始化并行，不存在已证明的串行等待关系。
  - 页面与代码版本映射明确，但未提供可读取的代码仓库。
- 推断：
  - 同步初始化是当前最高优先级的候选瓶颈，因为它在关键内容出现前持续占用主线程。
  - 现有 Evidence 不支持把数据请求判定为该场景的串行阻塞点。
- 产出：
  - 优先验证延后非关键初始化，或将初始化拆成可让出主线程的阶段。
  - 每次实验只改变一种初始化策略；固定页面版本、设备、浏览器、网络及缓存条件，多次重采 Trace。
  - 同时比较关键内容可见时间、主线程任务和初始化持续时间。
  - 行为验证覆盖主要流程、导航、错误处理以及依赖初始化的功能。
- 未确认：
  - 420ms 中实际可消除或可延后的比例。
  - 初始化与用户终点之间的完整因果关系。
  - 改造后的稳定收益。

## Case 04

### W04-A｜实际决策、边界、产出和状态

- 状态：`complete`，表示当前诊断链成立，不表示优化收益已经验证。
- 事实：
  - Trace 观察到路由进入时，目标产物执行约 300ms。
  - Source Map 将主要函数映射到目标路由源文件。
  - 该路由文件同步导入重型功能模块。
  - 页面、产物与代码版本一致。
- 推断：
  - Trace → Source Map → 路由源文件构成直接运行时映射。
  - 路由源文件 → 同步 Import → 重型模块构成高强度候选根因链。
  - 同步 Import 的存在仍不能证明全部 300ms 都来自被导入模块。
- 方案比较：
  1. 动态加载：若模块不是首屏必需，潜在收益较高；风险是组件延迟、加载失败和交互可用性变化。
  2. 延后初始化：保留模块加载语义，仅推迟非关键工作；风险是依赖初始化时序的功能失效。
  3. 减小模块：适合模块确属首屏必需的情况，行为风险相对较低，但改动范围和验证成本可能更高。
- 验证：
  - 分别建立三个独立实验，每次只改变一种策略。
  - 固定页面、产物和代码版本，以及设备、网络、缓存和操作流程。
  - 多次重采 Trace，比较用户可见终点、目标产物执行和主线程长任务。
  - 行为验证覆盖组件展示、交互、加载态、错误态、导航和回退。
- 未确认：
  - 重型模块是否为首屏必需。
  - 动态加载是否一定改善用户终点。
  - 三种方案各自可获得的稳定收益。

## Case 05

### W05-A｜实际决策、边界、产出和状态

- 状态：`partial`。
- 事实：
  - 容器先加载共享运行时。
  - 远程模块加载与容器级请求并行。
  - Trace 显示共享运行时存在主线程成本。
  - 可用仓库只包含远程模块。
  - 缺少其他页面的对照 Evidence。
- 范围划分：
  - 容器：负责页面编排和容器级请求，当前无代码映射。
  - 共享运行时：存在可观察的主线程成本，但不能自动归属于远程模块。
  - 远程模块：只能在其仓库范围内检查入口、同步依赖和初始化。
  - 页面自身：缺少对照，无法分离页面特有成本与共享成本。
- 推断：
  - “性能问题完全由远程模块导致”不成立；现有 Evidence 只能支持多层共同参与的候选模型。
  - 远程加载与容器请求并行，因此没有证据将二者描述为串行阻塞。
- 产出：
  - 在远程模块范围内，通过对应 Source Map 或性能标记确认自身执行区间。
  - 对已确认的远程非关键工作，分别验证拆分、延后初始化或减小模块。
  - 每次仅修改一个远程模块变量，并保持容器和共享运行时版本不变。
  - 多次比较用户可见终点、远程模块执行区间和主线程任务；同时验证加载态、错误态、导航和远程模块功能。
- 未确认：
  - 共享运行时成本的实际所有者。
  - 容器代码和页面自身的具体贡献。
  - 远程模块是否为主要瓶颈。

- 未虚构容器文件、调用路径或实现机制。
- 未声称问题完全由远程模块导致。
- 未因 Evidence 不完整而否定远程模块范围内的调查价值。

  - 缺少容器仓库及对应版本映射，无法定位容器和共享层职责。
  - 缺少其他页面对照，无法区分共享成本与页面特有成本。
  - 容器、共享运行时和页面自身的代码级归因均为 `inconclusive`。
