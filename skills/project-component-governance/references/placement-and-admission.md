# 放置与准入决策

## 决策类型

### `reuse`

核心语义、状态和交互已经一致，差异可通过现有参数、插槽、文案或样式配置解决。

### `wrap`

已有组件覆盖核心能力，只需要在业务侧增加默认值、数据转换、上下文连接或轻量布局。包装层不应复制底层状态机。

### `extend`

已有组件缺少一个具有普遍价值且可向后兼容的能力。扩展前必须核实其他调用方和默认行为。

### `new-local`

需要新建，但复用范围尚未被证明，或能力明显依赖当前页面、流程、权限和业务数据。先放在最小合理范围。

### `promote`

已有本地组件被多个独立场景实际需要，且已经具备稳定的公开边界，可以提升到项目共享或标准层。

## 放置层级

| 层级 | 适用条件 |
| --- | --- |
| 页面本地 | 单一页面、一次性编排或强业务依赖 |
| 应用共享 | 同一应用多个独立页面复用，但仍依赖应用上下文 |
| 项目共享 | 多个应用复用，公开 API 稳定，依赖可被共同消费 |
| 项目标准 | 项目共享能力已具备契约、索引、兼容和验证要求 |

层级不是质量排名。不要为了显得“通用”把组件提前提升。

## `promote` 准入问题

全部回答清楚后才建议提升：

1. 是否存在至少两个独立、可核实的复用场景？
2. 是否已经搜索并排除近似组件？
3. 提供的是稳定 UI 能力，还是某个流程的业务编排？
4. 公开 API 是否与单一页面的数据结构和权限模型解耦？
5. 样式、运行时和重依赖是否能被所有目标消费方正确加载？
6. 是否具备组件契约、发现索引和统一公开导出？
7. 是否有与风险相匹配的 Story、测试或消费方验证？
8. 是否明确版本兼容、维护责任和未来废弃方式？

“以后可能复用”不是复用证据。第一个使用方可以保留本地；出现真实第二使用方时再评估提升。
