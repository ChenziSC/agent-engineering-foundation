# 失败模式

| 失败模式 | 问题 | 修正 |
| --- | --- | --- |
| 每个任务都执行 Bootstrap | 重复 Host 原生代码探索并消耗上下文 | 只在存量项目接入、长期层缺失或明确重建候选时触发 |
| 把新会话恢复当作 Bootstrap | 混淆会话读模型与项目治理接入 | 新会话使用采用方 Context Resolver；本 Skill 只生成长期候选 |
| 把无 Harness 当作长期 fallback | 接入前状态被固化，项目无法获得后续 Resolver 和门禁 | 先做 `init plan`、候选审核和授权 Harness 化，完成后进入正常工作流 |
| 先执行 `init` 再推导项目事实 | 通用 Starter 不能生成项目规则、Knowledge 和入口，且可能遇到未知冲突 | 先运行只读 `init plan`，再生成和审核候选，最后另行授权写入 |
| 要求目标项目先安装 Harness 或生成 Section Index | 把接入工具变成目标项目前置依赖 | 从本仓运行只读计划；目标项目接入前无需已有 Harness |
| 为证明候选扫描整个仓库 | 成本和敏感内容暴露面失控 | 从目标模块与公开契约开始，候选可裁决后停止 |
| 只列文件，不说明长期价值 | 不能支持准入或刷新决策 | 说明职责、Evidence、建议动作、目标位置和刷新条件 |
| 把搜索未命中当作不存在 | 动态注册和外部消费者可能不可见 | 标为 `partial` 或 `unresolved`，说明检查边界 |
| 把文档描述当作当前事实 | 文档可能过期 | 对照公开契约、实现、测试和 revision，保留冲突 |
| 新候选直接标为已批准 | 越过采用方所有权和审核 | 新候选保持 `draft`；只识别有批准证据的既有内容 |
| 自动沉淀所有发现 | 易变实现和任务状态污染长期层 | 使用 `no-admission` 保留在当前报告或 Spec |
| 没有 revision 仍称可复核 | 后续无法判断证据是否变化 | 记录 revision；不可用时写明快照并将报告降为 `partial` |
| 把局部取证升级为 Slice 产品 | 重复 Host 能力并暗示不存在的完整性 | 仅为候选验证读取最小实现；字段级语义切片另走 Adapter 候选 |
| 报告完成即自动写入 | 混淆分析结果、授权和批准 | `ready-for-review` 只表示可裁决，写入和批准分别处理 |
| Registry 已有内容但 README 仍是通用 Starter | 机器可以路由，人和新 Agent 无法快速发现知识全貌 | 增加简明项目总览、正文链接和常见路由；机器事实仍由 Registry 与 Code Entry Map 持有 |
| README 复制完整 Registry 和路由表 | 人类导航成为易漂移的第二机器事实源 | 只保留用途与示例，链接机器文件并声明其权威性 |
| 把完整安装当成完整就绪 | Distribution 与 Doctor 只能证明内容和受管记录一致 | 逐项补适用性、项目配置与 Adapter 评估 |
| 安装时一次问完所有领域问题 | 大量问题与当前项目无关且会重复 | 先自动取证，合并共享决策，只询问无法证明且影响采用状态的内容 |
| 搜索无结果就判定不适用 | 缺少设计、埋点或组件配置不等于维护者拒绝采用 | 无明确项目事实或维护者决策时保留 `unresolved` |
