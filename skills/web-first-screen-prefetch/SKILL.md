# Web 首屏预请求

## 目标

从用户可见的首屏完成条件出发，找出发送过晚的关键只读请求，判断它是否具备安全提前发送的资格，并产出证据边界明确、行为优先的方案和验证计划。

不要预设预请求一定是最优方案。先比较修复挂载时机、延后非关键工作、减少串行依赖等替代方案。

## 开始前

确认至少具备：

- 可稳定描述的页面或路由；
- 当前实现代码或等价实现说明；
- 明确的用户场景；
- 可观察的首屏完成条件。

缺少任一项时，先列出需要补充的信息。可以继续提出有限假设，但必须把状态标记为 `blocked` 或 `partial`，不能直接给出实施结论。

## 工作流

1. 定义页面场景和可见完成条件。
2. 收集或整理浏览器、代码和版本 Evidence。
3. 画出从页面启动到关键内容可见的请求瀑布。
4. 选择一个或少量候选请求，并说明它们为何阻塞可见终点。
5. 按资格规则检查副作用、幂等、鉴权、缓存、契约、失效和降级。
6. 比较预请求与其他候选方案，选择改动最小且可验证的方案。
7. 先设计行为验证，再设计性能对比。
8. 使用报告模板输出结论、Blocker 和版本边界。

执行每一步时，按需读取：

- 分析阶段和退出条件：[workflow.md](references/workflow.md)
- 请求资格与拒绝规则：[request-eligibility.md](references/request-eligibility.md)
- Evidence、Claim 和版本边界：[evidence-and-version-boundaries.md](references/evidence-and-version-boundaries.md)
- 常见失败与修正方式：[failure-modes.md](references/failure-modes.md)

## 硬性门禁

- 拒绝写请求、一次性请求和无法确认副作用的请求。
- 不因 URL 相同就认定线上协议、鉴权、参数或缓存契约一致。
- 不把 Agent 推断描述成浏览器或代码事实。
- 缺少支持证据时使用“未证实”“无法判断”或 `blocked`，只有存在直接反证时才能使用“不成立”或 `refuted`。
- 没有版本映射时，只说明当前 Evidence 覆盖的版本范围。
- 正常、空态、错误或权限场景任一回归时，不得输出“优化成功”。
- 不自动修改代码、部署、发布或绕过人工确认。

## 输出

复制并填写 [analysis-report-template.md](assets/analysis-report-template.md)。输出至少包括：

- 场景与可见完成条件；
- Evidence 与 Claim；
- 候选请求和资格判断；
- 消费方契约；
- 替代方案比较；
- 最小改造计划；
- 行为验证；
- 性能比较方法；
- 版本边界、Blocker 和最终状态。

最终状态只能是：

- `ready`：证据足以进入实现，但尚未验证结果；
- `partial`：至少存在一项有用且范围明确的观察或建议，但不足以完成用户要求的闭环结论；
- `blocked`：无法形成有用的范围内结论，或者候选存在未解除的安全、契约或实施阻塞；
- `verified`：目标版本的行为验证通过，且性能比较成立。

状态选择规则：

1. 请求存在副作用、契约冲突或关键资格未知时使用 `blocked`，不能用 `partial` 降低安全门禁。
2. 运行页面与代码版本无法映射，但页面观察或代码审查仍有独立价值时使用 `partial`。
3. 关键输入不足且连范围内观察或方案都无法成立时使用 `blocked`。
4. `ready` 只表示可以进入实现，不表示已经取得收益。

使用 [behavior-validation-checklist.md](assets/behavior-validation-checklist.md) 检查行为结果。不要仅凭单个性能数字选择 `verified`。

## 实现请求

如果用户明确要求修改代码：

1. 先交付本 Skill 的分析结果；
2. 只修改报告中列出的最小范围；
3. 保留原请求消费方的契约；
4. 完成行为验证后再报告性能；
5. 仍然不执行部署或发布，除非用户另行明确要求。

## 资源决策

本 Skill 首期没有 `scripts/` 和 `tests/`。所有判断依赖 Agent、现有工具和人工确认；只有未来加入确定性 Validator 时，才增加对应脚本与测试。
