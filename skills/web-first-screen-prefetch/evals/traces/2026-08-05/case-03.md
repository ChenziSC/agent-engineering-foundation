## 2. 结论摘要

- 是否建议预请求：**不建议直接共享当前预请求结果**
- 最主要理由：预请求使用 `x-currency: USD`，原消费方使用 `x-currency: CNY`，两者请求契约不同；仅按 URL 建立缓存 Key 会发生缓存碰撞。
- 关键限制：无法证明服务端响应不受币种 Header 影响。直接共享可能让原消费方取得 USD 数据并按 CNY 展示。
- 安全门禁：必须先让请求 Header 与消费上下文一致，并将币种纳入缓存 Key，之后才能重新评估预请求资格。

## 9. 最小改造计划

- 最早安全发送位置：只有在目标币种、身份、区域和权限上下文稳定后才能发送。
- 原消费方：继续以自身完整请求契约获取或复用数据。
- 结果复用方式：仅复用方法、URL、Query、影响响应的 Header、身份上下文及转换契约均一致的结果。
- 避免重复请求：采用完整语义 Key，例如包含 `item=42`、`currency=CNY`、身份或租户范围；不能继续只使用 URL。
- 失效方式：币种、身份、租户或区域变化时失效或隔离对应记录。
- 错误回退：预请求缺失、失败或契约不匹配时，原消费方按原路径重新请求。
- 最小改动范围：请求 Key 构造逻辑、预请求参数来源以及原消费方的结果复用判断；没有代码 Evidence，不能指定具体文件。
