## Case 01

### P01-A：实际决策、产出与状态

- 最终状态：`ready`
- 候选资格：`eligible`
- 场景终点：合成商品详情页的主图可见，且价格不再显示占位。

事实：

- 只读目录请求在详情组件挂载后发送。
- 响应直接提供主图和价格，因此候选请求位于可见终点的数据依赖路径上。
- 请求无副作用、允许重复；身份、权限、参数在路由加载前稳定。
- 缓存 Key 覆盖商品、语言和身份变化；原消费方可复用同一 Promise。
- 失败 Promise 会被移除，原消费方仍保留原请求和错误路径。
- 页面与实现说明具有一致的合成版本标识。

推断与 Claim：

- 当前瀑布可表示为：路由进入 → 详情组件挂载 → 目录请求发送 → 数据返回 → 主图和价格渲染。
- “组件挂载后才发送”是可解释的晚触发点；响应直接提供两项关键内容，故提前发送可能缩短可见终点等待时间。
- 该 Claim 只证明存在可优化路径，不证明已经获得性能收益。

资格检查：

| 维度 | 结论 |
| --- | --- |
| 副作用 | 只读，无已知副作用 |
| 幂等 | 允许重复发送 |
| 鉴权 | 提前发送时身份和权限已稳定，Header/Cookie 与原请求一致 |
| 参数 | 商品和语言参数在发送前可确定 |
| 缓存 Key | 覆盖商品、语言及身份变化，不跨上下文复用 |
| 消费契约 | 原消费方可等待并复用同一 Promise |
| 失效 | 参数或身份变化使用新 Key，旧结果不会写入新页面 |
| 降级 | 失败 Promise 被清除，原请求和错误路径继续生效 |

方案比较：

- 预请求：在路由阶段启动单个目录请求，原消费方复用结果；改动集中于请求启动和共享职责。
- 提前挂载详情组件：也可能提前请求，但会改变组件生命周期，并可能提前执行与首屏无关的初始化；现有材料不足以证明范围更小。
- 延后非关键工作或减少其他串行依赖：当前没有对应阻塞证据，暂不作为首选。
- 结论：优先设计路由阶段预请求，同时保留原消费路径。

最小实现职责：

- 在身份、商品和语言参数稳定后的最早路由职责位置启动请求。
- 由共享请求缓存或数据加载职责持有 Promise；不指定未经代码 Evidence 支持的文件名。
- 原消费方使用相同完整 Key 复用 Promise，避免重复请求。
- 导航、参数或身份变化时隔离并失效旧结果。
- 预请求失败时清除失败项，使原消费方能够重新请求并沿用原错误处理。

验证计划：

- 正常：主图和价格正确出现，Loading 结束，确认消费方复用了预请求结果。
- 空态：空结果结束 Loading，显示既有空态且不污染其他 Key。
- 错误：预请求失败后原路径仍会请求，不无限重试。
- 权限：未授权时不越权提前访问；权限变化不复用旧结果。
- 重复进入与导航：没有重复请求或旧页面结果串用。
- 性能：在相同版本、入口、缓存和网络条件下区分首次与重复访问；多次记录请求开始时间及可见终点，比较中位数和尾部分布。

## Case 02

### P02-A：实际决策、产出与状态

- 最终状态：`blocked`
- 候选资格：`blocked`
- 被阻断的 Claim：“可以在路由加载阶段提前发送资源领取请求。”

事实：

- 候选为改变服务器状态的资源领取操作。
- 操作具有一次性语义。
- 重复调用可能发生冲突并产生额外审计记录。

推断与结论：

- 副作用和非幂等性直接违反预请求资格门禁，因此提前发送 Claim 被现有 Evidence 反驳。
- 客户端缓存或 Promise 去重只能减少部分客户端重复调用，不能消除服务端写入、重放、冲突或额外审计语义。
- 用户希望提速不改变该安全边界。

Blocker：

- 写请求会在用户正常领取时机之前改变服务器状态。
- 重复或重放可能造成额外可观察影响。
- 缺少可观察完成条件等其他输入，但即使补齐也不能解除上述副作用门禁。

只读替代方向：

- 可以考虑提前读取“是否具备领取资格、资源展示信息或领取前置状态”的只读接口。
- 该替代请求仍须单独确认副作用、鉴权、缓存 Key、失效和错误降级；实际领取动作必须保留在原有授权和用户操作时机。

## Case 03

### P03-A：实际决策、产出与状态

- 最终状态：`blocked`
- 当前候选资格：`blocked`
- 核心原因：完整请求契约不一致，且缓存隔离错误。

契约差异：

| 契约项 | 预请求 | 原消费请求 | 判断 |
| --- | --- | --- | --- |
| 方法 | GET | GET | 相同，但不足以证明可复用 |
| URL及商品参数 | 相同 | 相同 | 仅证明地址层面一致 |
| 货币 Header | 一种货币范围 | 另一种货币范围 | 不一致 |
| 缓存 Key | 仅按 URL | 仅按 URL | 未包含影响结果的货币维度 |
| 结果语义 | 第一种货币价格 | 第二种货币价格 | 不可互换 |
| 身份、Cookie、失效、错误策略 | 未提供 | 未提供 | `inconclusive` |

事实：

- 两条请求的货币 Header 不同。
- 当前缓存 Key 仅使用 URL，因此不同货币结果可能命中同一缓存记录。

推断与 Claim：

- URL 相同不能证明请求契约一致。
- 错误货币结果被消费属于行为正确性回归，不是单纯的性能偏差。
- 在缓存 Key 和结果隔离修复前，不得共享预请求结果。

修复方向：

- 按实际服务契约将货币以及所有影响结果的身份、语言、区域或租户维度纳入缓存 Key。
- 不同完整 Key 使用隔离的 Promise 和结果。
- 原消费方只能复用与自身完整请求契约匹配的记录。
- 修复后重新检查副作用、鉴权、消费契约、失效和降级，不能仅复查 HTTP 方法。

验证计划：

- 正常场景：分别验证两种货币下金额、符号和格式正确。
- 跨币种场景：快速切换、并发打开、前进后退及缓存命中时不得串用结果。
- 进一步检查参数变化后的失效、预请求失败回退、错误、权限及重复进入。
- 只有行为验证通过后，才比较请求发送时间和价格可见终点。

## Case 04

### P04-A：实际决策、产出与状态

- 最终状态：`partial`

事实：

- 本地实现说明具有一个明确的合成代码版本标识。
- 用户提供的 Network 记录显示目标请求较早发送。
- Network 记录不含页面构建标识，页面发布时间也未确认。

证据边界：

- 代码侧只能确认本地说明属于指定代码版本；材料不足以证明该版本已部署。
- 页面侧可以确认记录中的请求较早发送。
- 两类 Evidence 无法建立版本映射，因此不能把页面观察归因于本地方案。

Blocker：

- 运行页面是否对应目标代码版本尚未证明。
- 时间接近、请求较早或记录生成时间都不能代替页面—制品—代码映射。

最短 Verification：

1. 从页面构建标识、响应 Header、静态制品清单或等价发布证据中取得运行版本。
2. 将运行制品映射到目标代码版本。
3. 在该明确版本上重新记录同一页面场景，确认请求发送顺序。
4. 若要升级为 `verified`，还需完成正常、空态、错误、权限行为验证，以及同条件性能比较。

## Case 05

### P05-A：实际决策、产出与状态

- 最终状态：`blocked`
- 行为结论：存在空态回归，当前不能认定优化成功。

事实：

- 报告中的主图可见时间中位数从 1200ms 降至900ms。
- 正常数据场景通过。
- 错误场景能够回到原请求路径。
- 空结果会使页面永久停留在 Loading。
- 页面与代码版本关系明确。

推导与结论：

- 报告范围内的中位数改善为300ms，约25%；该数据对正常场景具有参考价值。
- 永久 Loading 违反空态行为门禁和用户可见完成条件。
- 因存在直接行为反证，“整体优化成功”这一 Claim 不成立。
- 性能改善不能覆盖空态回归；当前不得输出 `verified`。

修复与重新验证计划：

1. 明确空响应在共享 Promise、缓存和消费方中的完成语义。
2. 确保空结果结束 Loading，并进入既有空态展示和操作路径。
3. 确认空结果缓存不会污染正常、其他参数或其他权限范围。
4. 重新验证正常、空态、错误、权限、重复进入、快速导航和预请求失败回退。
5. 所有行为场景通过后，在相同版本、缓存、网络和样本条件下重新比较请求时间及用户可见终点。
6. 修复前可保持方案阻断；若需要临时控制风险，应停用受影响路径的预请求，而不是忽略空态。
