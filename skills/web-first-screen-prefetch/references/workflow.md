# 分析工作流

## 阶段 1：定义场景

记录：

- 页面或路由；
- 用户进入方式；
- 登录、区域、权限等前置条件；
- 用户真正等待的内容；
- 可见完成条件。

可见完成条件必须可观察，例如“主图可见且价格不再显示占位”，不能只写“页面加载完成”。

退出条件：场景可以被另一位执行者复现，且完成条件可以通过 DOM、截图或明确状态观察。

## 阶段 2：整理 Evidence

优先收集：

- Network 请求开始、结束和依赖关系；
- DOM 或渲染状态变化；
- 触发请求的代码位置；
- 请求消费方；
- 页面与代码版本关系。

没有工具时，可以使用用户提供的 Trace、HAR、截图或实现说明，但必须标记来源和范围。

退出条件：至少有 Evidence 支持“请求何时发送”和“关键内容何时可见”。缺一项时只能继续做有限分析。

## 阶段 3：建立瀑布

按时间顺序描述：

```text
路由进入
→ 组件或模块初始化
→ 前置依赖完成
→ 候选请求发送
→ 数据转换
→ 关键内容可见
```

区分：

- 真正的串行依赖；
- 代码组织造成的晚触发；
- 与可见完成条件无关的并行工作；
- 仅仅时间接近但没有因果证据的事件。

退出条件：能够解释候选请求为何晚于最早安全发送时机。

## 阶段 4：选择候选

候选请求应同时满足：

- 与可见完成条件直接相关；
- 发送时间存在可以解释的延迟；
- 有明确消费方；
- 具备检查请求资格所需的信息。

不要一次选择大量请求。优先选择一个收益路径最清晰的候选。

退出条件：每个候选都有对应 Evidence 和阻塞关系 Claim。

## 阶段 5：检查资格

读取 [request-eligibility.md](request-eligibility.md)，逐项检查：

- 副作用；
- 幂等；
- 鉴权；
- 参数和缓存 Key；
- 消费方契约；
- 失效；
- 错误、空态和权限降级。

任一阻塞条件无法确认时，把候选标记为 `blocked`，不要用低置信度绕过。

## 阶段 6：比较方案

至少比较：

1. 提前发送候选请求；
2. 修复请求触发或组件挂载时机；
3. 延后与首屏无关的初始化；
4. 减少前置串行依赖；
5. 保持现状。

按预期收益、行为风险、改动范围和验证成本排序。

退出条件：能够解释为什么选择预请求，或者为什么不应该使用预请求。

## 阶段 7：设计实现

方案至少说明：

- 最早安全发送位置；
- 请求结果如何被原消费方复用；
- 如何避免重复请求；
- 如何保持鉴权、参数和缓存一致；
- 失败时如何回退到原路径；
- 需要修改的最小文件或模块。

不要在没有代码 Evidence 时虚构具体文件路径。

## 阶段 8：验证

先验证行为：

- 正常；
- 空态；
- 错误；
- 权限；
- 重复进入或刷新；
- 预请求失败后的原路径回退。

再比较性能：

- 使用同一场景；
- 控制缓存和网络条件；
- 区分首次与重复访问；
- 同时记录请求时间和可见完成时间；
- 保留版本对应关系。

任何行为回归都会阻止 `verified`。
